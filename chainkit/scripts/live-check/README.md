# Live check

Exercises the P-Chain models against the deployed Fuji Data API and reports what
parsed. It exists because this SDK can no longer be regenerated by Speakeasy, so
schema drift has to be caught by calling the real API rather than by diffing
generated output.

It hits the network and reads live chain state. It is deliberately not wired into
`npm test`.

## Run it

```bash
npm run build          # the script resolves @avalanche-sdk/chainkit -> dist
npm run check:live
```

To check it the way a consumer would see it, link the built package into a
scratch project instead:

```bash
npm run build && npm link
mkdir /tmp/chainkit-consumer && cd $_
npm init -y && npm pkg set type=module dependencies.@avalanche-sdk/chainkit='*'
npm link @avalanche-sdk/chainkit
cp <repo>/chainkit/scripts/live-check/{check,fixtures}.mjs .
node check.mjs
```

Declare the dependency before linking. A later `npm install` in that project
prunes any linked package that isn't in `package.json`, and the failure looks
like an unrelated module-resolution error.

## Type surface

`types.ts` is not run; it is compiled, to assert the shapes a TypeScript consumer
actually gets:

```bash
npx tsc --noEmit --strict --module nodenext --moduleResolution nodenext \
  --target es2022 --skipLibCheck scripts/live-check/types.ts
```

Two things it pins down. `getBalancesByAddresses` returns an undiscriminated
P/X/C union, so reading a P-Chain field needs a narrowing step even though
`blockchainId` was the literal `"p-chain"`. The validator union, by contrast,
does discriminate on `validationStatus`, which is how you reach `autoRenew`.

## Fixtures

`fixtures.mjs` reuses the identifiers from the glacier-api record/replay tests
(`apps/glacier-api/test/integration/tests/primary-network/p-chain/`) so both
sides assert against the same Fuji positions.

Those tests replay recorded cassettes; this one does not. A fixture whose live
state has moved on will diverge here first — that is a signal about the fixture,
not necessarily about the SDK.
